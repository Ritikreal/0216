# AL Roadmap — Performance First, Local First

## Product goal

AL is a local-first desktop assistant for Arch Linux + Hyprland. It should feel responsive and polished, with a cinematic Spider-Man/Peter-Parker-style assistant HUD as inspiration: a compact floating/dynamic-island interface, a living core, clear listening/thinking/speaking states, and useful contextual feedback. Treat the film UI as a visual direction, not a pixel-for-pixel copy.

The priority order is:
1. Fast, reliable interaction.
2. Useful desktop skills with explicit safety boundaries.
3. A polished UI that reflects real assistant state.
4. Resource use and idle behavior optimized without making replies slower just to save power.

CPU/RAM use can be higher when that makes AL meaningfully faster. Keep the app responsive and avoid unnecessary background work, duplicate model instances, and expensive animations when hidden or idle.

## Non-negotiable principles

- Local-first: audio capture, transcription, and configured speech output stay on-device. No cloud transcription fallback.
- No arbitrary shell execution generated by a language model.
- Desktop actions go through typed skills with explicit allow/confirm/block policies.
- UI is a client of the assistant runtime; it must not contain its own duplicate intent or action logic.
- Keep the first release modular and testable. Do not add a framework or dependency unless it provides a concrete benefit.
- Do not claim hardware testing based on CI or code inspection. Validate on the user's Arch/Hyprland machine.
- Keep configuration backward-compatible where practical and document migrations.

## Phase 0 — Repository and architecture baseline

- Keep main as the integration branch.
- Review code and tests before each feature; make small, reversible commits.
- Define boundaries between audio, STT, TTS, intent/router, skills, runtime, and UI bridge.
- Add architecture and developer setup documentation.
- Keep secrets, local model weights, recordings, and machine-specific config out of Git.

**Exit gate:** clean install instructions, test suite passes, clear module boundaries, no accidental network fallback.

## Phase 1 — Reliable voice loop (current priority)

- Pin AL to the laptop's built-in microphone through the PipeWire source configuration; do not silently jump to a headset microphone.
- Measure and log audio RMS/peak in an opt-in diagnostic mode; do not print sensitive audio or save recordings by default.
- Make calibration robust to quiet rooms, ambient noise, short speech, and queue overruns.
- Use adaptive voice detection with sensible minimum/maximum utterance lengths and a clear timeout.
- Avoid Whisper VAD discarding short phrases; validate empty transcripts before routing.
- Keep model loading lazy for one-shot CLI use and warm once for persistent use. Never instantiate multiple models unnecessarily.
- Improve local transcription latency and accuracy with measured settings, not guesswork.
- Make failures actionable: distinguish no audio, no speech, empty transcript, STT failure, and unavailable skill.

**Exit gate:** repeated short and normal utterances work consistently; silence is not mistaken for speech; no-transcript cases recover cleanly; all recognition remains local.

## Phase 2 — Fast assistant runtime and speech output

- Create one persistent runtime that owns the loaded STT model, TTS process, cancellation state, and skill registry.
- Add local Piper TTS configuration, verify the selected voice file exists, and test the audio output route.
- Reduce perceived latency: warm the model once at startup, avoid repeated process/model initialization, and measure capture/STT/TTS timings.
- Support cancellation and clean interruption. Never let stale audio accumulate.
- Keep response generation and skill execution separate from audio device callbacks.

**Exit gate:** an end-to-end request works repeatedly without restarting AL; response timing is measured; TTS can be disabled without breaking the assistant.

## Phase 3 — Safe skill architecture

- Define a typed skill interface with name, description, arguments, execution result, timeout, and policy.
- Policies: SAFE for read-only/low-risk actions, CONFIRM for consequential actions, BLOCKED for prohibited actions.
- Do not execute arbitrary natural-language shell strings. Each desktop operation maps to a known implementation with validated arguments.
- Add an auditable local action log that avoids storing raw microphone audio and minimizes sensitive content.
- Add tests for unauthorized actions, invalid arguments, timeout, cancellation, and failure recovery.

**Exit gate:** every skill has a clear policy and tests; dangerous/unimplemented requests fail closed.

## Phase 4 — Desktop integration

- Add a user-level systemd service with explicit environment and reliable shutdown/restart behavior.
- Integrate a Hyprland Super+A push-to-talk shortcut and visible capture state.
- Ensure one active listener and predictable microphone ownership.
- Add local status/diagnostic commands; normal use should not require a terminal.
- Keep startup and service failures visible and recoverable.

**Exit gate:** AL starts reliably in a Hyprland session, the hotkey works, and microphone/service errors can be diagnosed.

## Phase 5 — First useful desktop skills

Prioritize a small, dependable set:
- Help and identity.
- Time/date and basic system status.
- Read-only system diagnostics.
- A few explicit desktop controls with confirmation where needed.
- Clear unsupported-skill responses.

Only add a skill when its implementation, permissions, failure behavior, and tests are defined. Browser automation, arbitrary scripts, file deletion, and other high-impact actions are not initial skills.

**Exit gate:** the initial skill set works end-to-end through voice and has policy tests.

## Phase 6 — UI/UX: cinematic HUD

Build the visual layer after the runtime contract is stable, so UI work does not block audio and skill development.

- Use Quickshell/QML if it fits the installed Arch/Hyprland stack and can be kept responsive.
- Visual direction: dark/near-black glass, restrained cyan/teal highlights, a recognizable animated core, subtle scan/energy effects, and precise typography.
- Compact top-edge dynamic island expands only when useful; avoid a permanently large chat window.
- States: idle, listening, processing, speaking, running action, confirmation needed, success, and error.
- Show what AL heard and the result of an action; sensitive data should not be exposed in persistent overlays.
- Animations should be GPU-conscious, state-driven, and pause/reduce when hidden or idle. Smoothness matters more than decorative effects.
- UI communicates with the runtime through a small, documented local IPC interface; it never executes skills directly.

**Exit gate:** hotkey-to-HUD flow works, state transitions match real runtime events, and the UI remains responsive during STT/TTS.

## Phase 7 — Expansion and polish

- Improve natural-language understanding through a local model only if it improves capability enough to justify its memory/latency cost.
- Keep any model constrained to structured tool requests; validate every request against the skill registry and policy engine.
- Add more desktop skills, contextual history with local controls, focus tools, media controls, and diagnostics incrementally.
- Add benchmarks for cold start, warm response latency, idle memory, CPU usage, and UI frame pacing.
- Add regression tests for privacy, offline behavior, permissions, and service recovery.

## Performance strategy

- Optimize for fast perceived response, not the lowest possible resource consumption.
- Warm expensive models once in the persistent service; don't reload per turn.
- Benchmark before changing model size, compute type, beam size, audio thresholds, or dependencies.
- Prefer asynchronous I/O and bounded queues; drop stale audio rather than building latency.
- Keep UI animation independent of inference and stop unnecessary work when the HUD is hidden.
- Offer a lighter mode later if useful, but do not make it the default at the cost of responsiveness.

## Definition of done before UI/UX starts

- [ ] Local mic source is deterministic and documented.
- [ ] Repeated speech tests pass, including short utterances and silence.
- [ ] Empty transcripts and audio failures are handled distinctly.
- [ ] Local STT model stays warm in the persistent runtime.
- [ ] Local TTS works with a configured voice, or cleanly reports that it is disabled.
- [ ] Runtime/skill boundaries and action policies are tested.
- [ ] The first useful skills work end-to-end.
- [ ] Hotkey and user-service integration are reliable.
- [ ] A runtime/UI state contract is documented.
- [ ] Unit and integration tests pass on the supported environment.

## Current known status

The CLI can capture audio through the PipeWire route and locally transcribe at least some utterances. Short utterances have been inconsistent, and TTS/desktop integration are not yet verified end-to-end. The current energy-based VAD is a baseline, not a finished solution. Treat all phases after the voice-loop MVP as planned until tested on the target machine.
